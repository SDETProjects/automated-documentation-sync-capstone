# /step-2-architecture

**Design the system architecture based on requirements.**

## Role

Architecture specialist that translates requirements into component design, data flows, and APIs.

## Task

Read `claude-requirements.md` and generate `claude-architecture.md` with:
- **Component diagram:** Modules, services, dependencies
- **Data flow:** How data moves through the system
- **API contracts:** Interfaces between components
- **Technology choices:** Languages, frameworks, databases
- **Deployment topology:** How components are deployed
- **Traceability:** Each component addresses one or more requirements

## Context

- **Input:** `claude-requirements.md` (Step 1 output)
- **Output:** `claude-architecture.md`
- **Audience:** Developers, architects, reviewers
- **Integration:** Must align with existing codebase patterns

## Constraints

- Design must address all FRs and NFRs from Step 1
- Use existing code patterns and conventions from `src/`
- Identify external dependencies (APIs, databases, services)
- Sketch component interactions without over-engineering

## Inputs

1. `claude-requirements.md` (generated by Step 1)

## Outputs / Output format

```markdown
# Architecture — [Story ID]

## Overview
[1-2 sentences on the overall approach]

## Component Design

### [Component Name]
- **Purpose:** [What it does]
- **Responsibilities:** [Key tasks]
- **Dependencies:** [Other components it needs]
- **Requirements addressed:** FR-1, FR-2, NFR-1

### [Component Name]
...

## Data Flow

[ASCII diagram or description showing how data moves through components]

Example:
```
User Input → Validator → Processor → Storage
                                        ↓
                                    Cache
```

## API Contracts

### [Component API]
```
POST /api/endpoint
Input: {field: type, ...}
Output: {field: type, ...}
Errors: [HTTP status codes]
```

## Technology Stack

| Layer | Choice | Reason |
|---|---|---|
| Language | Python 3.11 | Matches repo |
| Framework | FastAPI | Lightweight, async |
| Database | PostgreSQL | ACID compliance (NFR-2) |
| Cache | Redis | Performance (NFR-1) |

## Deployment Topology

[Diagram showing how components are deployed: servers, containers, networks]

## Traceability

| Component | FR | NFR | Test strategy |
|---|---|---|---|
| Validator | FR-1, FR-2 | NFR-3 | Unit tests |
| Processor | FR-2, FR-3 | NFR-1, NFR-2 | Integration tests |
| Storage | FR-4 | NFR-1 | Contract tests |

## Risks & Mitigations (preview for Step 3)

| Risk | Impact | Mitigation |
|---|---|---|
| [Risk] | [Severity] | [Mitigation] |
```

## Completion criteria

- [ ] `claude-architecture.md` exists
- [ ] All components defined with purpose and dependencies
- [ ] Data flow documented (diagram or prose)
- [ ] API contracts specified for component boundaries
- [ ] Technology choices justified
- [ ] Traceability matrix connects components to requirements
- [ ] Architecture team can implement from this design
